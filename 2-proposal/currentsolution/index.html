Current proposal — a policy assistant for an accessories shop

Policy Assistant — current solution proposal

Document review: 6 November 2026. This AI-assisted proposal describes published code and the latest recorded deployment evidence. The student must review, practise and explain it. It does not establish FCAJ eligibility or authorize DEMO policies for real transactions. October proposals on the parent page remain historical records.

1. Problem, users and value

Small accessories shops repeatedly answer warranty, returns, delivery and payment questions. Scattered text encourages unsupported answers or incorrect conditions. Customers need an explicit handoff to a person when information is insufficient, while controlling what they share.

The solution serves one shop, with self-registering customers and trusted administrators. Customers consult policies, ask cited questions, use private PDFs and submit consented support requests. Administrators approve content, manage effective dates, coordinate cases and inspect aggregate feedback. This supports decisions; staff verify actual orders and damage causes outside the application.

GoalVerificationBoundary
Answers customers can inspectOpen source excerpts and PDF page referencesCitations do not prove every statement correct
Private customer dataTwo-user isolation, DTO and backend authorization checksApplication administrators are distinct from AWS operators
Avoid expired policiesUTC+07 dates, effective-state filtering and final source checksPoint-in-time checking, not a transaction lock around inference
Contextual staff handoverSelf-claim, notes, reason-required takeover and revision conflictsAll trusted administrators can read notes; no restricted staff role
Costs suitable for a small trialQuotas, bounded retrieval, budget alerts and usage monitoringNo new load benchmark, completed Calculator estimate or hard spending cap

2. Implemented scope and exclusions

Implemented: signup/email verification/PKCE/password recovery; private, version-pinned PDFs and text/OCR pipeline; policies/PDF/both source selection; cited answers; 30-day history; policy draft/publish/archive/restore/revision/audit; shop configuration; consented support with assignments and notes; aggregate answer feedback; account access blocking followed by background purge.

Not implemented: multiple tenants, order synchronization, payment/refund execution, social channels, automatic support email, SLA timers or a support-only role. The application does not decide real warranty eligibility. Policies remain DEMO until a real operator approves business content. Complete feature inventory and launch conditions.

3. Architecture inputs for the student’s own diagram

The following is a design description, not a replacement for a student-designed AWS diagram. Use correct AWS icons, identity boundaries, private customer data boundaries and model regions; compare with template.yaml before submission.

FlowComponents and responsibilities
Web applicationCloudFront + S3; Cognito authentication; HTTP API → Python 3.12 Lambda validates JWT/groups/ownership
Upload and processingPrivate versioned S3 → DynamoDB metadata/Stream → dispatcher → SQS → worker; IAM-isolated PDF parser, Textract for scans; recovery and DLQ
QuestionsApproved policies or the customer’s own extracted PDF → Cohere embeddings and S3 int8 vectors → bounded retrieval → Nova 2 Lite → output/source ID/effective-state validation → history
Administration/supportDynamoDB policy/shop/ticket records; revision + owner-deletion guard + audit transaction; customer DTO excludes internal notes
OperationsCloudWatch logs/metrics/alarms, SNS and AWS Budgets; PITR and Retain protect data during infrastructure operations

Application services, embeddings and Textract use Singapore; generation uses a Japan profile spanning Tokyo/Osaka. Do not claim all data remains in Vietnam or Singapore. Private PDFs are not automatically shared with staff; support requests are not AI retrieval material. No VPC/NAT or always-on vector database was added merely to increase the service count.

4. Technical decisions and risks

Risk / tradeoffMitigation and remaining measurement
Model inference errors or changing sourcesAccept retrieved source IDs only, validate structure and recheck public facts before saving; no new accuracy result
Cross-account accessJWT-derived ownership, backend checks, private S3 and customer DTO allowlists; AWS operators retain separate infrastructure authority
Duplicate/failed background jobsVersion pinning, durable state, bounded retries, partial batch failures, recovery and DLQ; incident exercises need reviewed scope
Concurrent staff/customer writesRevision + transaction; conflict requires reload and review before retry
Scan and S3-vector scalingBounded retrieval/pagination; measure recall, latency and backlog before raising quotas or replacing storage
Costs beyond generationInclude all S3 versions, PITR, logs/alarms, OCR, transfer and failed requests; budgets only alert
Deletion and recoveryBlock account access before purge; documented retention; logs/backups have separate lifecycles; no new restore acceptance
